Architecture logicielle

Comment savoir si une décision technique est "architecturale" ou pas ? Une seule question suffit.

Pas besoin de diagramme UML ni de titre ronflant. La question à se poser avant toute décision structurante : si on se trompe, combien ça coûte de revenir en arrière ?

Renommer une méthode, changer un for en foreach : réversible en quelques minutes, c'est du design. Choisir comment deux services communiquent, ou si un modèle de données est partagé entre équipes : ça peut coûter des semaines à défaire, c'est de l'architecture.

La distinction n'a rien d'universel — elle dépend du contexte réel du projet. Mais elle donne un réflexe simple à appliquer avant de foncer sur un new StripeClient() en plein milieu d'un contrôleur.

08 août sam. #3
Design Patterns

Un Singleton codé en dur et une instance "singleton" gérée par un conteneur d'injection de dépendances : ce n'est pas du tout la même chose.

Le premier impose l'unicité dans le code lui-même — constructeur privé, accès statique global — impossible à remplacer par un mock en test. Le second reste un objet ordinaire, injectable, testable : seule sa portée est configurée comme singleton par le conteneur (Spring, Symfony...), qui pourrait tout aussi bien lui donner un scope différent sans changer une ligne de code métier.

Le vrai reproche fait au Singleton classique, ce n'est pas le pattern en lui-même : c'est l'état global caché qu'il introduit, avec des dépendances invisibles entre des parties du code qui semblent indépendantes.

Signal d'alerte assez fiable en entretien comme en revue de code : si vos tests unitaires doivent réinitialiser un état statique entre deux exécutions, un Singleton est probablement en cause quelque part.

Tests

Écrire des tests, c'est installer des détecteurs de fumée dans une maison.

Les poser prend du temps et ne rend la maison ni plus grande ni plus belle. Mais le jour où un départ de feu se déclare, c'est le détecteur — pas la vigilance humaine — qui alerte à temps pour agir avant que les dégâts deviennent irréversibles.

Sans détecteur, la maison peut très bien fonctionner des années sans incident. Le problème n'est pas la probabilité qu'un incident arrive un jour donné, c'est le coût le jour où il arrive sans qu'on l'ait vu venir.

Un point qu'on oublie souvent en entretien : un test ne prouve jamais l'absence de bug en général. Il prouve seulement qu'un comportement précis, pour une entrée précise, produit la sortie attendue. Le vrai coût des tests, ce n'est pas de les écrire — c'est de ne pas les avoir le jour où il faut modifier le code en confiance.

13 août jeu. #5
Bases de données

Question d'entretien qui a l'air facile : quelle différence entre une clé primaire et une clé étrangère ?

La clé primaire identifie une ligne de façon unique dans sa table. Elle ne peut jamais être nulle, jamais dupliquée — et une table n'en a qu'une seule.

La clé étrangère, c'est différent : c'est une colonne qui pointe vers la clé primaire d'une AUTRE table, pour créer une relation. Une table peut en avoir plusieurs.

Ce qui surprend souvent : une relation en base relationnelle n'a rien de magique. "commande.client_id" ne contient rien d'autre que la valeur de l'id d'un client qui existe déjà ailleurs. Pas de lien caché, juste une colonne qui référence une valeur.

Si le client déménage, on corrige une seule fiche dans la table clients. Toutes ses commandes restent valides sans qu'on ait à toucher une seule ligne de plus.

Cloud & DevOps

CAPEX vs OPEX, la vraie bascule du cloud, en 30 secondes.

Avant le cloud, on achetait des serveurs : un coût fixe, amorti sur plusieurs années, dimensionné pour le pic de trafic le plus haut qu'on pouvait imaginer — même si ce pic n'arrive qu'à Noël et que le serveur tourne à 5 % le reste de l'année.

Le cloud transforme ça en coût variable : on paie à la seconde ce qu'on consomme réellement. Ce n'est pas juste "le serveur de quelqu'un d'autre", c'est surtout l'élasticité — la capacité d'ajuster les ressources à la demande, automatiquement, en quelques minutes plutôt qu'en quelques semaines.

Le piège que beaucoup découvrent trop tard : une ressource oubliée mais jamais éteinte continue d'être facturée. Un serveur physique, on le voit tourner dans un coin du datacenter. Sur le cloud, ce coût-là reste invisible jusqu'à la facture.

20 août jeu. #8
Architecture logicielle

Port primaire, port secondaire : si vous confondez les deux en entretien, ça se voit tout de suite.

L'architecture hexagonale (Ports & Adapters, formalisée par Alistair Cockburn en 2005) tient sur une image simple : une prise électrique murale. Elle définit un contrat standard, sans savoir ce qu'on va y brancher — une lampe, un chargeur, un aspirateur.

Un port primaire, c'est ce qui pilote le métier : un contrôleur HTTP ou une commande CLI qui déclenche une action. Un port secondaire, c'est l'inverse : le métier qui appelle l'extérieur, pour persister une donnée ou envoyer un e-mail, sans jamais connaître l'implémentation réelle derrière.

Le nombre six dans "hexagonale" n'a rien de spécial, au passage — Cockburn voulait juste assez de faces pour montrer qu'un métier peut avoir plusieurs ports, pas seulement une entrée et une sortie comme le suggérerait un rectangle.

Design Patterns

Si vous retrouvez le même bloc if ($type === 'email') { ... } elseif ($type === 'sms') { ... } copié-collé à cinq endroits du code, vous avez besoin d'une Factory.

Le Factory Pattern déplace cette logique de décision dans un seul endroit dédié : une méthode ou une classe dont le seul travail est de créer le bon objet selon un paramètre. Le code appelant ne fait plus jamais new EmailNotification() lui-même — il demande une notification de type email, sans savoir quelle classe concrète il reçoit en retour.

Le jour où un nouveau canal apparaît (WhatsApp, par exemple), un seul endroit à modifier, pas cinq.

Un point que beaucoup ratent en entretien : Factory viole en partie le principe ouvert/fermé, puisqu'ajouter un type oblige à modifier le switch. C'est un compromis assumé — concentrer la modification en un point identifié, plutôt que la disperser partout.

Tests

Question piège sur le TDD : pourquoi faut-il VOIR le test échouer avant d'écrire le code, l'étape Red ?

La réponse n'est pas "parce que c'est la règle". Voir le test échouer d'abord prouve que le test teste réellement quelque chose : s'il passait déjà sans code de production, il ne vérifierait rien d'utile, ou testerait le mauvais fichier.

C'est une vérification du test lui-même, avant de lui faire confiance pour valider le futur code.

Deuxième piège fréquent : le TDD garantit-il un code sans bug ? Non. Il structure la façon d'écrire le code et produit une bonne couverture par construction, mais il ne protège que contre les cas que les tests couvrent explicitement. Un dev qui oublie un cas limite au moment d'écrire le test aura un code TDD... qui ne le couvre pas non plus.

27 août jeu. #11
Bases de données

DELETE et TRUNCATE suppriment tous les deux des lignes. Les confondre en entretien (ou en prod) coûte cher.

DELETE est une commande DML : elle supprime ligne par ligne, peut être filtrée avec un WHERE, déclenche les triggers, et peut être annulée avec un ROLLBACK dans une transaction.

TRUNCATE est une commande DDL : elle vide toute la table d'un coup, réinitialise le compteur d'auto-incrément, ne se filtre pas, et n'est généralement pas journalisée ligne par ligne — donc beaucoup plus rapide sur un gros volume, mais moins flexible et souvent impossible à annuler selon le moteur.

La bonne réponse en entretien n'est pas de réciter la définition, c'est de dire QUAND utiliser l'un plutôt que l'autre : DELETE pour un nettoyage ciblé et réversible, TRUNCATE pour vider une table de logs qu'on sait pouvoir sacrifier entièrement.

Cloud & DevOps

Question piège classique en entretien DevOps : Kubernetes, c'est du IaaS ou du PaaS ?

La réponse honnête : ni vraiment l'un ni vraiment l'autre. Un cluster managé (EKS, GKE) est fourni comme un service, ce qui se rapproche du PaaS. Mais vous continuez à gérer vous-même les conteneurs, leur configuration et leur déploiement — ce qui garde une bonne part de responsabilité côté IaaS.

On parle parfois de CaaS (Container as a Service) pour désigner ce niveau intermédiaire. Si un candidat répond "PaaS" sans nuancer, c'est souvent le signe qu'il récite une définition plutôt qu'il ne comprend la logique derrière.

La vraie question derrière IaaS, PaaS et SaaS, ce n'est pas le vocabulaire : c'est "qui gère quoi", et jusqu'où on est prêt à déléguer du contrôle contre moins de charge opérationnelle.

03 septembre jeu. #14
Architecture logicielle

Un "Client" en facturation et un "Client" en support technique ne sont pas le même objet. Et c'est très bien comme ça.

Un système qui grossit accumule presque toujours des mots ambigus. Le mot "Client" finit par désigner un compte de facturation pour une équipe, un contact commercial pour une autre, un utilisateur connecté pour une troisième — et une classe unique de 40 attributs que plus personne ne comprend vraiment.

Le Domain Driven Design ne cherche pas à unifier ce mot de force. Il découpe le système en bounded contexts, des frontières explicites à l'intérieur desquelles un mot a un sens unique et précis. "Client" peut légitimement vouloir dire deux choses différentes en Facturation et en Support, tant que chaque contexte reste cohérent avec lui-même.

C'est exactement comme le mot "pièce" : un architecte, un comptable et un déménageur n'en ont pas la même définition, et aucun des trois n'a tort.

05 septembre sam. #15
Design Patterns

L'Abstract Factory facilite l'ajout d'un nouveau thème complet. Elle complique beaucoup plus l'ajout d'un seul nouveau composant.

Ajouter une nouvelle famille — un "Thème contraste élevé", par exemple — revient à ajouter une nouvelle factory concrète, sans toucher au code existant. Le principe ouvert/fermé est respecté à la lettre.

Mais ajouter un nouveau type de produit à une famille déjà en place — un composant Menu déroulant, en plus du Bouton et de la CaseACocher — oblige à modifier l'interface UIFactory, puis toutes les factories concrètes existantes. C'est le vrai point faible du pattern, celui qu'on oublie souvent de mentionner en entretien.

Le signal qui doit faire penser à Abstract Factory plutôt qu'à une Factory simple : plusieurs objets qui doivent varier ensemble selon un même contexte, où un mélange entre familles serait un vrai bug — pas juste un détail esthétique.

08 septembre mar. #16
Tests

Une équipe teste calculerRemise() en isolation, le test passe toujours. En production, la remise ne s'applique jamais.

La cause : la requête SQL qui récupère le statut fidélité du client renvoie la mauvaise colonne. Le test unitaire n'a rien vu, car il ne testait que la logique de calcul, pas la façon dont les composants s'assemblent réellement.

C'est exactement la différence entre les deux niveaux. Un test unitaire répond à "cette logique, prise isolément, se comporte-t-elle comme prévu ?". Un test d'intégration répond à "ces composants, assemblés ensemble, produisent-ils le résultat attendu ?"

Les deux questions sont différentes, et aucune ne remplace l'autre. Se contenter de tests d'intégration parce que "c'est plus proche de la réalité" a un coût réel : ils sont plus lents, et un échec est plus difficile à localiser — la cause peut venir de n'importe quel composant impliqué.

10 septembre jeu. #17
Bases de données

Erreur fréquente chez les devs qui découvrent les index : indexer toutes les colonnes "pour être tranquille".

Un index accélère la lecture, mais il a un coût réel : chaque INSERT, UPDATE ou DELETE doit aussi mettre à jour l'index. Plus une table a d'index, plus les écritures ralentissent.

Et un index n'est même pas toujours utile. Sur une colonne peu sélective — un booléen "actif" par exemple, avec seulement deux valeurs possibles — le moteur préfère souvent un scan complet plutôt que de suivre l'index. Trop peu de valeurs distinctes, pas assez de gain.

La bonne question n'est pas "combien d'index" mais "quelles colonnes sont réellement filtrées, jointes ou triées dans mes requêtes réelles". EXPLAIN ANALYZE existe justement pour vérifier ça au lieu de le supposer.

12 septembre sam. #18
Cloud & DevOps

L'erreur la plus fréquente que j'entends sur Docker : "c'est une VM plus légère".

Non. Une VM virtualise du matériel et embarque son propre système d'exploitation complet — plusieurs gigaoctets, démarrage en minutes. Un conteneur partage le noyau de la machine hôte et n'isole que l'espace utilisateur — quelques dizaines de mégaoctets, démarrage en une seconde.

La distinction à vraiment connaître pour un entretien : image vs conteneur. Une image est un modèle figé, comme une classe. Un conteneur est une instance en cours d'exécution de cette image, comme un objet. On peut lancer dix conteneurs identiques à partir d'une seule et même image.

Détail technique que peu de devs citent spontanément : chaque instruction d'un Dockerfile crée une couche mise en cache. Placer les instructions qui changent le moins souvent avant celles qui changent tout le temps accélère nettement les rebuilds.

Architecture logicielle

Le signal le plus fiable d'un couplage fort dans du code : un new NomDeClasseConcrete() planté au milieu d'une méthode métier.

C'est la question qu'on pose souvent en entretien pour vérifier qu'on sait reconnaître le problème, pas juste le définir. Deuxième signal, tout aussi fiable : si on ne peut pas tester une classe sans faire tourner une vraie base de données ou un vrai service externe, c'est qu'elle dépend d'une implémentation concrète plutôt que d'une abstraction.

La correction ne demande pas un gros chantier : une interface, et l'injection de la dépendance par le constructeur au lieu d'un new en interne. Résultat, on peut remplacer Stripe par un autre prestataire de paiement sans toucher à la classe qui l'utilise.

Attention à l'excès inverse, cela dit : créer une interface pour une simple fonction utilitaire sans effet de bord n'ajoute que de l'indirection, sans aucun bénéfice réel.

Design Patterns

Un constructeur avec dix paramètres optionnels a un nom : le "constructeur télescope". Et c'est illisible à l'appel.

Impossible de savoir quel argument correspond à quel paramètre sans rouvrir la signature complète — et chaque appelant se retrouve à passer null pour tout ce qu'il n'utilise pas.

Le Builder résout ça en séparant la construction en étapes chaînées, chacune nommée explicitement : methode(), header(), timeout(). Le code appelant devient auto-documenté, et une méthode finale construire() valide l'ensemble avant de retourner un objet fini, généralement immuable.

Signal d'alerte à repérer en code review : au-delà de quatre ou cinq paramètres optionnels sur un constructeur, ou plusieurs constructeurs qui se chevauchent pour couvrir toutes les combinaisons possibles. C'est le moment de sortir un Builder plutôt que d'ajouter un onzième paramètre.

Tests

Un stub, c'est un figurant qui répond toujours la même réplique préparée à l'avance. Un mock, c'est l'huissier de justice qui note qui a dit quoi, à qui, et combien de fois.

Dans un test, le stub joue son rôle sans qu'on l'interroge sur son passé. Le mock, lui, est interrogé après l'action pour confirmer que les bonnes interactions ont bien eu lieu.

Ce qu'on ne dit pas assez : abuser des mocks rend un test fragile. Un mock vérifie le comment (quelles méthodes appelées, avec quels arguments) — un détail d'implémentation. Changez la façon d'obtenir le même résultat métier sans changer le résultat observable, et le test casse alors que rien de réel n'a changé.

Détail utile en entretien : PHPUnit distingue explicitement createStub() et createMock(). Jest, plus permissif, utilise jest.fn() pour les deux usages — la différence tient alors uniquement dans la présence d'un toHaveBeenCalledWith().

24 septembre jeu. #23
Bases de données

Question piège classique : le serveur plante une seconde après un COMMIT. Vos données sont perdues ?

Non — et c'est tout l'intérêt de la Durabilité, le D d'ACID. Une fois qu'une transaction est validée par COMMIT, le moteur a déjà écrit les changements dans un journal des transactions (write-ahead log) sur disque, avant même de confirmer au client que c'est bon.

Au redémarrage, la base rejoue ce journal et retrouve exactement l'état validé. Rien n'est perdu, même si le crash survient littéralement une milliseconde après.

Ce qui piège souvent en entretien, c'est la suite : la différence entre Atomicité et Isolation. L'Atomicité protège une transaction en elle-même (tout ou rien). L'Isolation protège les transactions les unes des autres. Deux garanties, deux problèmes différents — et confondre les deux dans une réponse trahit vite une compréhension de surface.

26 septembre sam. #24
Cloud & DevOps

Ce qu'on vous demande vraiment quand on vous pose une question sur Kubernetes en entretien.

Rarement "c'est quoi Kubernetes". Plutôt : "Pod, Deployment, Service, quelle différence ?" Le Pod est l'unité d'exécution la plus petite. Le Deployment décrit l'état désiré — combien de réplicas, quelle image — et gère les mises à jour progressives. Le Service donne une adresse réseau stable vers des Pods qui, eux, changent d'IP à chaque redémarrage.

Le concept qui sépare vraiment les candidats préparés des autres : la boucle de réconciliation. Vous déclarez "je veux 3 réplicas", et le contrôleur agit en continu pour que l'état réel corresponde à cet état désiré, en recréant un Pod qui crashe sans aucune intervention humaine.

Une bonne image mentale pour retenir tout ça : un régulateur de flotte de taxis qui redirige un client vers un autre véhicule si le sien tombe en panne, sans jamais que le client appelle un taxi précis par son numéro.

Architecture logicielle

Une astuce simple pour savoir si une classe a trop de responsabilités : décrivez ce qu'elle fait en une phrase, sans utiliser le mot "et".

Si la phrase devient "elle valide les données et calcule le prix et envoie un e-mail", le diagnostic est fait — plusieurs responsabilités sont mélangées dans la même unité de code.

Une responsabilité, ce n'est pas une méthode ni une ligne de code : c'est une raison de changer. Le vrai symptôme apparaît quand des équipes différentes, pour des raisons totalement indépendantes, finissent par modifier le même fichier — le service marketing change l'e-mail, la compta change le calcul du prix, et la classe entière tremble à chaque fois.

Le principe s'applique à toutes les échelles, pas seulement à une classe : un module "facturation" qui contient de la logique de stock viole exactement le même principe, juste à une échelle plus grande.

Design Patterns

Si vous avez déjà écrit addEventListener ou utilisé un EventEmitter en Node.js, vous connaissez déjà l'Observer Pattern — même sans l'avoir jamais nommé.

Le principe : un Subject notifie automatiquement tous ses abonnés dès qu'un état change, sans avoir besoin de connaître leur nature exacte. Un statut de commande qui passe à "payée" peut déclencher un e-mail, un SMS et une notification à l'entrepôt, sans que la classe Commande sache rien de ces trois services.

L'erreur la plus fréquente avec ce pattern n'est pas conceptuelle, elle est opérationnelle : oublier le désabonnement. C'est la cause la plus courante de fuite mémoire liée à l'Observer, particulièrement en JavaScript avec des écouteurs d'événements jamais retirés.

Autre point à connaître pour un entretien un peu poussé : le pub/sub n'est pas l'Observer, c'en est une évolution distribuée — un intermédiaire (message broker, event bus) s'intercale, et émetteurs et abonnés ne se connaissent plus du tout entre eux.

La question qui sépare un dev junior d'un dev senior en entretien SQL : quelle différence entre un non-repeatable read et un phantom read ?

Un non-repeatable read, c'est relire la même ligne deux fois dans une transaction et obtenir une valeur différente, parce qu'une autre transaction l'a modifiée et validée entre-temps.

Un phantom read, c'est différent : c'est ré-exécuter le même SELECT avec un critère (WHERE statut = 'en_cours') et obtenir un ensemble de LIGNES différent, parce que d'autres lignes correspondant au critère ont été insérées ou supprimées entre-temps.

Le premier porte sur une ligne qui change de valeur. Le second porte sur des lignes qui apparaissent ou disparaissent. Read Committed empêche le premier problème sans résoudre le second — il faut monter jusqu'à Serializable pour éliminer les deux.

Ce n'est pas une question de vocabulaire. C'est une question qui révèle si on sait raisonner sur la concurrence, pas juste écrire des requêtes isolées.

Question piège en entretien : Adapter et Decorator enveloppent tous les deux un objet. Quelle différence ?

Beaucoup de devs répondent par une définition floue apprise par cœur, et se plantent sur l'essentiel.

Bases de données

Un email de client recopié sur dix commandes différentes. Le jour où il déménage, il faut corriger dix lignes — en oublier une, et vous avez deux vérités pour la même personne.

C'est ce qu'on appelle une anomalie de mise à jour, et c'est exactement le problème que la normalisation résout. Trois règles progressives : 1NF (chaque cellule contient une seule valeur, pas de liste cachée dans une colonne), 2NF (chaque colonne dépend de la clé primaire entière), 3NF (chaque colonne dépend UNIQUEMENT de la clé primaire, jamais d'une autre colonne).

Dans une table "commandes" avec client_nom et client_email à plat, l'email dépend du nom du client, pas de l'id de la commande — c'est une dépendance transitive, et c'est le piège le plus fréquent qui empêche d'atteindre la 3NF.

En entretien, on n'attend pas de réciter les sigles. On attend qu'un candidat regarde une table dénormalisée et propose spontanément le découpage en tables reliées par des clés.

Pourquoi Express, PSR-15 et ASP.NET utilisent tous le même design pattern sans le nommer, en 30 secondes.

Le concept de middleware, dans n'importe quel framework web, c'est du Decorator Pattern pur.

Chaque middleware enveloppe le traitement suivant, ajoute un comportement (log, auth, compression), puis délègue à la couche d'après — en respectant toujours la même interface que ce qu'il enveloppe.

Mettre un TTL infini sur ses clés Redis "pour être tranquille" est une fausse bonne idée.

Sans TTL, une clé jamais invalidée explicitement — bug applicatif, oubli dans le code — reste périmée indéfiniment en mémoire. Et la mémoire de Redis se remplit progressivement de données obsolètes que personne ne va nettoyer.

Le TTL n'est pas la stratégie d'invalidation elle-même, c'est un filet de sécurité. La vraie invalidation, la fiable, c'est de supprimer explicitement la clé juste après chaque écriture en base (DEL après un UPDATE), pour refléter le changement immédiatement plutôt que d'attendre l'expiration.

Même avec ça, une fenêtre de risque existe : entre l'écriture en base et l'invalidation du cache, une lecture concurrente peut voir une valeur périmée pendant un court instant. Un TTL raisonnable en complément limite les dégâts si l'invalidation explicite est ratée.
